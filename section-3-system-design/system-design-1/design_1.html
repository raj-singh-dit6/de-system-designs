Datawarehouse Governance Strategy

1 · Dedicated application identities

Each application retrieves its own credential from a secrets manager. People never share or use application login roles.

analytics_app_user sales_app_user logistics_app_user
→

2 · Database user groups

Each login is a member of exactly one NOLOGIN group. Permissions are managed on the group, never on individual application users.

analytics_app_group · sales_app_group · logistics_app_group

→

3 · Least-privilege access

The group receives narrow grants to approved views or controlled functions. Base-table access is denied unless the application needs it.

LOGIN app user → NOLOGIN group → grants

Analytics application

analytics_app_user → analytics_app_group

PurposeRead-only sales and membership analysis through approved reporting views.

No data changes.

Sales application

sales_app_user → sales_app_group

PurposeMaintain the product catalogue and safely retire old products.

No member or sales-transaction access.

Logistics application

logistics_app_user → logistics_app_group

PurposeView order weights and mark eligible transactions as completed.

No unrestricted transaction changes.

Design principle: application users authenticate; database user groups authorize.

Logistics application
logistics_app_group		 analytics.v_logistics_order_weights
analytics.mark_order_completed(order_id) 		GRANT SELECT ON logistics view GRANT EXECUTE ON completion function Read total items weight and change eligible orders to completed through a guarded function. No direct UPDATE, INSERT, DELETE, or unrestricted fact-table access.

Role membership

GRANT analytics_app_group TO analytics_app_user;

GRANT sales_app_group TO sales_app_user;

GRANT logistics_app_group TO logistics_app_user;

Baseline safeguard

REVOKE ALL ON SCHEMA analytics FROM PUBLIC;

Then grant only the capabilities listed above. Group roles remain NOLOGIN; only the three application users can authenticate.
